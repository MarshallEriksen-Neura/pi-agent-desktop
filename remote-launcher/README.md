# Pi Desktop remote launcher

`pi-desktop-launcher` is the fixed remote entrypoint used by Remote Agent Mode. The desktop application starts system OpenSSH and invokes this file with an opaque Base64 payload. In run mode, the launcher's stdout is reserved exclusively for Pi's JSONL RPC stream.

## Requirements

The remote host must provide:

- POSIX `/bin/sh`
- `base64` with either the GNU `-d` or BSD/macOS `-D` decode option
- Node.js, reachable either on the noninteractive `PATH` or from a login shell (see below)
- Pi installed and authenticated on the remote host
- The configured workspace as an absolute POSIX path

Authentication, Pi settings, skills, MCP configuration, Git configuration, and SSH keys remain on the remote host. The profile stored by the desktop app contains no secrets. Provider sync is a separate, user-initiated capability: it can copy only selected provider definitions and explicitly approved API keys over SSH stdin. OAuth tokens, command credentials, resolved local environment secrets, and provider-scoped `env` values are never transferred.

## Install

The desktop app installs this file for you: **Settings › Remote agent**, fill in the host and workspace, press **Check**, then press **Install** on the launcher row. The app copies the launcher over the same SSH policy it uses at runtime, resolves `$HOME/.local/bin/pi-desktop-launcher` (no sudo), and stores the absolute path it wrote. The copy is embedded in the app binary, so it cannot drift from the build.

To place it manually instead, install it anywhere on an absolute path and set that path under **Advanced › Launcher path**:

```sh
install -m 0755 pi-desktop-launcher ~/.local/bin/pi-desktop-launcher
```

Configure the host in `~/.ssh/config` on the desktop machine and verify that noninteractive authentication and strict host-key validation already work:

```sh
ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes build-host true
```

Remote Agent Mode does not handle password, MFA, keyboard-interactive, or first-use host-key prompts. Add or verify the host key outside the app before running preflight.

## Finding Node.js and Pi

`ssh host command` runs a **non-interactive, non-login** shell. It reads only `$BASH_ENV` — never `~/.bashrc` or `~/.profile` — and Debian's stock `~/.bashrc` returns early on `case $- in *i*) ;; *) return;; esac`, before any version-manager block. So nvm, fnm, volta and asdf put `node` on the *interactive* `PATH` and nowhere the launcher can see it. `node -v` works when you SSH in by hand and `ssh host node -v` fails on the same host.

When `node` is not already on the `PATH`, the launcher asks a login shell (`bash -lc`, then `zsh -lc`) for its `PATH` and **appends** it. Appending rather than prepending means anything already reachable keeps priority, so a host that works today cannot be changed by this. The same recovery is what makes an nvm-installed `pi` findable, since it lives in the same `bin` directory. Hosts with neither bash nor zsh fall back to the usual absolute locations (`~/.nvm/versions/node/*/bin`, `~/.local/share/fnm/…`, `~/.volta/bin`, `~/.asdf/shims`, `/usr/local/bin`, `/opt/homebrew/bin`); no version is chosen among them, so pin one with a symlink if it matters.

`--preflight` reports the interpreter it ended up on as `nodePath`, which the desktop app shows next to the version — a path under `.nvm` or `.volta` there is the visible sign that this recovery happened.

To check what a login shell resolves:

```sh
ssh build-host bash -lc 'command -v node; command -v pi'
```

## Protocol

The launcher accepts fixed internal modes. The desktop owns every SSH argument and the stored launcher path; renderer-provided values are never interpreted as shell, executable, environment, `HOME`, or arbitrary CLI argv.

- `--capabilities`: takes no payload and writes one JSON document to stdout. Launcher revision 18 advertises `run-v1`, `preflight-v1`, provider sync, detached task/attach, workspace read/write, repository review (`repository-read-v1`), safe single-file/commit mutations (`repository-write-v1`), generation-bound batch staging (`repository-batch-write-v1`), repository sync and local branches (`repository-phase3-v1`), reviewed fast-forward integration (`repository-integration-v1`), reviewed Merge/Rebase integration (`repository-integration-v2`), and independently gated PI-management capabilities: `pi-packages-read-v1`, `pi-packages-mutate-v1`, `pi-skills-read-v1`, `pi-skills-mutate-v1`, `pi-cli-read-v1`, and `pi-cli-update-v1`. Revision 15 resolves effective Git identity through one bounded read-only command and injects only validated author/committer fields. Revision 16 adds GCM-only HTTPS authentication: system/global helper configuration is read without exposing it to mutations, only exact `manager` or `manager-core` values with trusted executable provenance are accepted, helper chains are reset, and prompts remain disabled. Revision 17 rejects every C0/DEL control character in trusted proxy configuration and aligns HTTPS preflight ordering with the desktop implementation by validating proxy policy before credential-helper selection. Revision 18 adds fixed Pi CLI version inspection and explicit update operations that run in remote `$HOME`, independent of a workspace. Repository reads and each write generation remain independently gated. `launcherRevision` identifies functional launcher builds; `statusVersion` changes only when the detached `status.json` schema changes.

  A launcher older than capability discovery answers `invalid launcher mode` with exit 64, which is byte-identical to what a corrupt launcher returns. The desktop therefore treats an unanswered query as a V1 baseline rather than a broken host. Reinstall the launcher (**Settings › Remote agent › Install**) to enable newer features. Read and mutation capabilities are checked separately, so a read-only launcher remains browsable while every mutation control fails closed.
- `--preflight`: validates the workspace and runs `pi --version`; writes one JSON document to stdout. Alongside `ok` it reports `piVersion`, `nodeVersion`, `nodePath`, and `piAuthConfigured` — the last is a nonempty-`auth.json` check, which the app surfaces as a warning rather than a blocker because pi exposes no way to query login state noninteractively.
- `--run`: starts `pi --mode rpc` in the remote workspace; stdout remains Pi JSONL and launcher diagnostics go to stderr.
- `--provider-sync`: reads one provider-sync protocol v1 request (maximum 2 MiB) from stdin. The fixed `inspect` and `apply` actions merge selected provider configuration while preserving existing remote credentials and unrelated entries. Provider JSON and credentials never appear in argv, environment variables, or diagnostics.
- `--manage`: reads exactly one management protocol v1 JSON envelope from stdin and writes exactly one JSON reply to stdout. It supports `inspect`, `readSkillSource`, `browseSkillSource`, `mutatePackage`, `mutateSkill`, `inspectPiCli`, and `updatePiCli`. Package and skill operations require an absolute `remoteCwd`; Pi CLI operations require `remoteCwd: null` and run from remote `$HOME`. The Pi executable is injected by the desktop from the stored profile, while the renderer can request only the fixed semantic operation. The global scope is always remote `$HOME/.pi/agent`; the project scope is always `<remoteCwd>/.pi`. Skill source reads use opaque SHA-256 references issued by `inspect`, never renderer-provided paths.
  Revision 18 keeps the revision 17 envelope for package and skill operations; only Pi CLI operations add the backend-owned `piExecutable` field, so older launchers continue to serve their advertised management capabilities.
- `--repository`: accepts one base64-encoded repository protocol v1 request. `status` returns porcelain v2 metadata for the workspace; `diff` returns one staged or unstaged file diff after revalidating the declared repository root. Revision 7 added generation-checked single-file `stage`/`unstage` and staged-only `commit`. Revision 11 adds bounded `stagedDiff`, explicit-remote `fetch`, reviewed-upstream `push`, and local `createBranch`/`switchBranch`. Revision 12 adds separately capability-gated, reviewed fast-forward integration. Revision 13 adds separately capability-gated, reviewed Merge and linear Rebase with verified automatic abort on conflicts. Revision 14 adds independently gated `stageBatch`/`unstageBatch`: 1–4096 exact reviewed entries, a 16 KiB cumulative UTF-8 path budget, NUL-delimited stdin pathspecs, one temporary-index Git operation, pre-install generation/worktree revalidation, and one index installation. Every write revalidates workspace/repository identity, authoritative generation, and conflict/operation state before Git runs, then returns a fresh status snapshot with upstream, merge-base, remote, and local-branch metadata. Paths, refs, and reviewed object IDs are passed to fixed Git arguments without shell interpolation. Git output is bounded, and oversized diffs are rejected or returned with `truncated: true` according to the operation.

Repository mutation replies are deliberately fail-closed. Success includes the authoritative `repoRoot`, porcelain status, current repository operation, upstream metadata, displayed remotes and local branches, plus `commitOid` for commits. Failures include a stable `reason`, optional `detail`, and `applied`; `applied: true` means the write may have reached the live repository but an authoritative result could not be established. Batch failures conclusively occurring before live-index installation remain `applied: false`; transport or installation ambiguity is `refreshFailed`, `applied: true`. Phase 3, batch, and integration successes and failures use one strict operation-specific JSON document; incomplete snapshots, unknown reasons, extra fields, invalid UTF-8, multiple documents, and incoherent `applied` states fail closed. Phase 3 Fetch updates only the selected remote-tracking namespace: it uses atomic ref updates, disables tags, configured refmaps, `FETCH_HEAD`, submodule recursion, and hooks, and never merges, rebases, checks out, or stashes. Fetch and Push resolve and validate the effective remote URLs first, then pass the validated literal URL to Git so a later remote-name lookup cannot redirect the operation. Revision 16 binds HTTP(S) network children to a provenance-validated Git executable and invokes the reviewed canonical GCM executable by absolute path for HTTPS only; helper chains and interactive fallbacks are disabled. Push requires the reviewed local `HEAD` and upstream OID, remote, and branch; pins the source to the reviewed commit and destination; verifies that the reviewed upstream is an ancestor; uses an exact expected-OID lease against concurrent remote changes; requires exactly one effective Push URL; disables tags, submodule recursion, and hooks; compare-and-swaps the corresponding local remote-tracking ref only after success; and reports non-fast-forward rejection. Branch creation pins the new branch to the reviewed `HEAD`, never switches or tracks, and disables hooks; switching accepts only a displayed local branch, disables hooks, never stashes, and lets Git refuse files that would be overwritten. Executable, credential-bearing, proxying, or redirecting repository-local transport configuration is rejected before network access. This includes every repository-local `http.*` key, credential helpers, URL rewrites, case-varied unsafe keys, and unsupported URL schemes.

HTTP and HTTPS Fetch and Push keep global/system Git configuration disabled during network execution. Before any transport/configuration query, the launcher resolves Git from fixed root-owned operating-system locations and uses that canonical executable throughout the preflight and network operation. For compatibility, it restores only the URL-matched `http.proxy` value from explicit system and global scopes (without includes), accepts only bounded anonymous `http://` or `https://` proxy URLs, and injects that single value into the isolated Git command. An explicit empty global value disables a lower-scope proxy. Ambient proxy variables and repository/worktree-local proxy policy remain blocked; HTTPS alone receives the validated operating-system Git Credential Manager. Transport/configuration failures returned to the desktop use fixed redacted messages rather than raw Git diagnostics.

Phase 4A integration is deliberately separate from Fetch and never performs network access. The request pins the repository generation, checked-out local branch, `HEAD`, upstream remote/branch/OID, merge-base, and `strategy: "fastForwardOnly"`; all fields are revalidated immediately before mutation. Integration refuses unborn or detached `HEAD`, stale or unresolved upstreams, local divergence, dirty index/worktree, conflicts, active Git operations (including sequencer state), index locks, and ignored or untracked paths that the reviewed upstream would overwrite. It runs only `git merge --ff-only` against the reviewed upstream OID with hooks, autostash, statistics, editing, and submodule recursion disabled, then verifies the resulting branch and `HEAD`. It never pulls, creates a merge commit, rebases, stashes, resets, force-updates, or resolves conflicts. Once the merge process has started, a nonzero exit or any result that cannot be inspected or refreshed is conservatively reported as `refreshFailed` with `applied: true` so the desktop refreshes rather than presenting a potentially partial write as unapplied.

Phase 4B remains separate from Fetch and supports only the explicit `integrateMerge` / `mergeCommit` and `integrateRebase` / `rebaseLinear` pairs on clean, reviewed, diverged histories. It rejects safer fast-forward histories, merge commits in the reviewed rebase range, ranges above 256 local commits, unsafe effective Git configuration (including included and worktree-scoped filters, merge drivers, and branch merge options), and conservative ignored/untracked overwrite hazards across both sides of the reviewed history. Merge requires an already-trimmed, nonempty message of at most 4096 UTF-8 bytes, pins the reviewed upstream OID, and creates one exact two-parent commit preserving that message byte-for-byte. Rebase accepts no message, uses fixed `--onto <upstream> <merge-base>` semantics, and preserves the reviewed linear commit count. Hooks, editors, signing prompts, signature verification, autostash, rerere, update-refs, and submodule recursion are disabled. A failed Git process is treated as a conflict only when repository metadata confirms the matching Merge or Rebase operation; the launcher then aborts automatically and verifies the original branch, `HEAD`, clean state, unrelated local refs, operation markers, and lock absence. Verified restoration returns `integrationConflict` with `applied: false`; any ambiguous mutation, abort, restoration, or final graph returns `refreshFailed` with `applied: true`. The launcher emits exactly one JSON reply; for integration, the desktop also requires strict operation-specific success/failure shapes and rejects banners, multiple documents, unknown reasons, invalid UTF-8, or incomplete snapshots as transport ambiguity.
- Detached-task, attach, stop/send/status/reap, and workspace modes support the supervisor and target-scoped file bridge. Their arguments are fixed or opaque encoded protocol payloads; see the supervisor protocol document for lifecycle details.

Run/preflight payload protocol version `1` carries the remote workspace, Pi executable, and optional remote session path. Values are passed to Node's process APIs as arguments and are never evaluated as shell source.

### Management safety model

Management uses a separate short-lived SSH process; it never shares the `--run`, attached, detached, or attach data stream. Requests are limited to 64 KiB. Inspect/source reads time out after 30 seconds, source browsing after 120 seconds, and mutation after 300 seconds. Replies are limited to 2 MiB; CLI diagnostics to 64 KiB; one `SKILL.md` to 256 KiB; settings and package locks to 512 KiB each; package entries to 512 and skill entries to 2,048.

Every mutation carries the `stateToken` returned by `inspect`. The launcher acquires `$HOME/.pi/agent/.pi-desktop-management.lock`, performs a fresh inspect under that lock, and returns `stateConflict` rather than applying an operation to stale state. Live locks are never stolen. Locks older than ten minutes or owned by a missing PID are reclaimed through a separate reclaim lock and atomic quarantine rename. After the fixed PI/Skills CLI command ends—even with a nonzero status—the launcher performs another inspect and returns the authoritative snapshot. A skill move that installs the destination but fails to remove the source reports `halfDone: true`.

The launcher resolves only `pi`, `skills`, or the `npx -y skills@latest` fallback and constructs their allowlisted arguments itself. Long-running commands execute in a dedicated process group when `setsid` is available; timeout sends TERM and then KILL to the group. Snapshot settings expose only `packages`; package locks expose only package versions. Diagnostics are bounded and redact URL userinfo and common authorization, token, password, secret, and API-key forms.

## Lifecycle

Version 1 is attached to the SSH connection. Closing the app or stopping a conversation asks the launcher to terminate Pi, with a forced-kill fallback. Durable reattach, multi-client sharing, and guaranteed termination after network loss are not provided.

The SSH channel carries a liveness probe (`ServerAliveInterval=15`, `ServerAliveCountMax=3`), so a network partition ends the connection after roughly 45 seconds instead of leaving the desktop blocked on a socket that will never answer. What ends is the local `ssh` process: the remote Pi is terminated by SIGHUP forwarding, which requires the remote sshd to notice the dead peer first, and that can lag well behind. So after a partition the desktop reports the remote process status as **unknown** and does not reconnect on its own — a reconnect could start a second Pi against a session file the first one still owns. Recovery is an explicit restart.
